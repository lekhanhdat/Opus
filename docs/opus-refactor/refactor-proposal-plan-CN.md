# Opus Refactor 问题分析与技术方案总结

## 1. 背景

这次 Opus Refactor 讨论的核心，不是单纯把某几个慢接口或慢 Job 优化掉，而是要从当前已经暴露的问题出发，重新梳理 Opus 的代码结构、性能瓶颈、删除安全、第三方 API 复用方式、单元测试体系和未来架构演进方向。

目前会议中反复出现的关键词包括：

- SO Job、Scan&Archive、大客户 Job 速度慢，尤其是 Deletion only 场景效率低。
- Discovery 流程存在效率问题，目前已有 CI 或其他线索，但还需要具体化证据。
- Entity Framework 使用方式可能带来性能问题；SQL 相比 EF 更容易被显式控制、调优和解释。
- 如何确保删除逻辑的正确性，并且后续避免出现新的删除出错问题。
- Wrapper 的使用方式，以及 SharePoint CSOM、Microsoft Graph 等第三方 API 的调用方式，需要评估其合理性和正确性。

从 Support 回复客户的角度看，目前最大的问题不是没有做优化，而是缺少一个稳定的问题分析框架。客户问“为什么慢、为什么失败”时，我们需要能回答：慢的是哪个 Job、哪个阶段、哪段 SQL、哪个第三方 API。

因此，这次重构应该被定义为一次“面向长期稳定性的结构化改造”，而不是一次局部性能修补。我们要做的事情包括：把问题分类清楚，把复杂逻辑拆开，把可观测性补上，把高风险路径纳入单元测试，把第三方依赖收敛到统一适配层，并在这次分析重构过程中为未来 Multi-Cloud 和 AI 辅助开发留下稳定边界。

## 2. 总体目标

1. 提升客户可感知性能。重点关注大客户、长时间运行 Job、Scan&Archive、Discovery、Deletion only 等场景。优化目标不能只看平均值，而要看 P95/P99、超时率、失败率和大客户场景下的稳定性。
2. 降低误删除风险。删除逻辑必须可解释、可预览、可审计、可恢复。对于 Support 和客户来说，我们需要能回答：为什么会删、删了什么、谁触发的、按什么策略删的、是否可以恢复。
3. 提高 Support 定位和回复效率。Support 面对客户问题时，需要从“感觉慢”转为“慢在哪个 Job、哪段 SQL、哪个第三方 API、哪个删除阶段”。这要求系统提供稳定的日志、trace、指标和问题分类模型。

## 3. 问题分类

### 3.1 SharePoint 性能问题

优先从小龙哥提供的 Sample Case 入手。经过分析，在 Library 下 Folder 过多的时候，存在较大的 Request 浪费，需要重构逻辑以降低 SP Object 构建次数和 Request 次数。

### 3.2 Entity Framework 性能问题

目前存在的问题是：大数据情况下的查询效率，以及 Timer Role 的内存过高。

EF 在简单 CRUD 上提高开发效率，但在复杂查询、大数据量、批量删除和多表 Include 场景中可能生成不可控 SQL。LINQ 表达式看起来简单，但最终 SQL 可能包含复杂 join、子查询、过多字段、重复查询或 N+1 问题。EF 的 Change Tracking、Lazy Loading、循环 SaveChanges、Include 过深等行为也可能造成性能退化。

这里的关键观点是：不要简单讨论“EF 好还是 SQL 好”。正确方案是按场景分层。普通 CRUD、低频查询、简单对象加载继续使用 EF；热点查询、复杂报表、大批量扫描、批量删除、跨表复杂过滤使用显式 SQL、Query Object 或 Stored Procedure。也就是说，EF 保留在适合它的地方，SQL 用在需要可控、可解释、可调优的地方。

建议建立 EF 使用规范：只读查询默认使用 AsNoTracking；禁止在循环中触发数据库查询；禁止不受控的 Lazy Loading；Include 必须有边界，避免一次加载过大对象图；大结果集必须分页或流式处理；批量更新和删除不应逐条 SaveChanges。

对于复杂查询，建议使用 Query Object Pattern，例如 FindDeletionCandidatesQuery、GetSlowJobSummaryQuery。每个 Query Object 负责一类查询，内部可以选择 EF、Raw SQL 或 Stored Procedure。业务层只表达意图，不关心底层实现。

关键查询还需要可观测与测试。每个关键查询要能输出最终 SQL，保留执行计划和索引建议。对热点查询建立 benchmark 或性能回归测试。对重要 Query Object 做 golden test 或 snapshot，防止重构后 SQL 形态发生不可接受变化。

### 3.3 第三方 API 性能：SharePoint CSOM、Microsoft Graph

这个问题建议具体问题具体分析。目前没有证据表明哪一个在具体场景上性能更优。我们会在解决具体问题时，分析是否为 API 性能问题。

### 3.4 代码结构问题

当前维护问题主要是大函数过多、逻辑耦合严重，EF、删除策略、第三方 API、日志和审计混在业务流程中。缺少清晰边界会导致修改任何部分都可能影响整个流程。如果架构没有稳定边界，未来每次新增能力都可能再次重构。

某些 Function 过大，逻辑定位困难，造成维护困难。我们将先从 SO Job 主逻辑入手，拆分并优化代码可读性，便于后续维护，同时尽量避免一次性大改。

### 3.5 降低误删除风险

会议中提到的一个想法是：删除等动作之前增加 Check List，Check List 中的 item 来自代码关键步骤的采样结果，以确保关键节点按预期路线执行。对于 Check List 中的 items，需要事先根据当前 case 场景来规划。这个想法需要后续结合代码进一步考察其效果和价值。

### 3.6 关于 Unit Test

我们对 Unit Test 的期待是作为现有逻辑的兜底，并且重点在于边界覆盖的全面性，而不是表面覆盖率。当前做 Unit Test 的最大障碍是：数据操作代码与逻辑层代码混在一起，需要先完成分离才适合做 UT；并且对于 SharePoint 这类较复杂的数据层，需要 Mock 的内容过多，也是推进 Unit Test 的主要障碍。

关于这里，我们还需要一个进一步的评估。

### 3.7 Support 回复与问题分析体系

从解决客户问题的角度，当前最需要的是可解释性。客户问为什么慢、为什么删除、为什么失败时，我们要能够给出结构化解释。

Support 需要回答三个层次的问题：

1. 这个问题属于哪一类：Job 慢、EF/SQL 慢、删除策略复杂或删除执行慢、第三方 API 慢或被限流、Discovery 慢、大客户数据量导致的容量问题。
2. 证据是什么：Job ID、Tenant、Customer、时间窗口、阶段耗时、SQL 耗时、API 耗时、throttling/retry 次数、删除候选数和实际删除数。
3. 当前状态是什么：已确认根因、正在验证假设、已修复待发布、需要客户提供额外数据。

我们需要总结在上述信息要求下，还缺失哪些 Telemetry、Log、Analysis 能力，并进行补全。

## 可执行方案汇总（持续更新中）

我们不会盲目开始重构，而是先以具体问题为起点和抓手，优先遵循小龙哥提供的问题优先级，在解决问题的同时制定细致更改方案。作为一个客户量已经较大的产品，我们会在确保稳定的基础上进行改动。

1. 第一优先级：以 RECO-37646 为例，解决 SO Job 中 Request 次数和 SP Object 构建次数过多的问题。
2. 第二优先级：慢 Job 的阶段化观测。理由是没有观测就无法证明优化是否有效，也无法向客户解释。
3. 第三优先级：EF 热点查询治理以及内存问题治理。重点是大量 Site 查询问题和 Timer Role 内存占用过高问题。
4. 第四优先级：Discovery Job 效率问题以及 Incremental 能力。会在转向 DAL 实现的同时，重点关注这两项问题的解决程度。
5. 第五优先级：从代码结构角度出发，以 Job 主逻辑为切入点优化和调整结构，提升可读性，并拆分大函数，尽量不动原有逻辑。
6. 第六优先级：CSOM/Graph API 的评估与调整。目标不是全面替换，而是从具体问题出发，评估某一部分或某一逻辑是否更适合 Graph API。
7. 第七优先级：单元测试网。进一步评估是采用小范围集成测试更优，还是追求大范围 Unit Test。
